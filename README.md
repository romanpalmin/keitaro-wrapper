# keitaro-wrapper

Тестовое задание: веб-обёртка над API рекламного трекера — создаватор кампаний и редактор офферов.

**Стек:** Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic, pytest.

## Запуск

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

cp .env.example .env   # заполнить KEITARO_API_KEY и другие значения

uvicorn app.main:app --reload
```

Сервис: http://127.0.0.1:8000  
Health: http://127.0.0.1:8000/health  
Swagger: http://127.0.0.1:8000/docs

## Миграции

URL БД берётся из `.env` (`DATABASE_URL`), не из `alembic.ini`.

```bash
alembic upgrade head      # накатить схему
alembic current           # какая версия сейчас
alembic revision --autogenerate -m "…"  # новая миграция (сравнение моделей с БД)
```

При старте сервиса (`uvicorn`):

- `APP_ENV=dev` (по умолчанию) — `lifespan` вызывает `init_db()`
  (`Base.metadata.create_all`): недостающие таблицы создаются автоматически;
  изменение существующей схемы — всё равно через миграции.
- `APP_ENV=production` — `create_all` **не** вызывается; схема только через
  `alembic upgrade head` (иначе downgrade в БД «молча» вернётся при рестарте).

## Редактор офферов: отличия от референса и почему упрощённо

В ТЗ к редактору сказано: кнопки работают, цифры верные; интерфейс — на наш вкус.
Оригинальный UX показан на видео из Notion (AdRobot: «Keitaro Streams» рядом с админкой Keitaro).

**Что в референсе:**

- кнопки **FETCH STREAMS FROM KT** и **PUSH TO KT | CANCEL** — правки сначала копятся локально, потом одним PUSH уходят в трекер;
- **REMOVE** не выкидывает оффер: share → 0%, пометка `(removed)`, кнопка **BRING BACK** (мягкое удаление);
- таблица со Stats/Trends, ссылка **VIEW IN KT**.

**Что у нас (упрощение):**

| Референс | У нас | Почему |
|----------|-------|--------|
| FETCH / PUSH / CANCEL | каждая кнопка **сразу PUT** в трекер | меньше состояний и источников рассинхрона: UI всегда = то, что в трекере. Локальный буфер (dirty-state, откат кнопкой CANCEL) — заметно больше кода и краевых случаев, а в ТЗ не требуется |
| REMOVE → 0% + BRING BACK | **hard-remove** из массива `offers` | проще контракт PUT: один массив после операции. BRING BACK — UX-удобство, не из ТЗ |
| Stats / Trends / VIEW IN KT | нет | данные отчётов трекера, вне «add/remove + цифры верные» |

**Что сохранено (суть ТЗ):**

- добавление/удаление офферов в кампании;
- **цифры верные**: после каждой операции `share` пересчитывается поровну, сумма всегда 100 (3 шт → 33/33/34 — как в видео).

**Существующие disabled-офферы** в массиве `offers` не выбрасываем: уходят в PUT с `state=disabled, share=0` и вне пересчёта активных (сумма 100 — только по активным).

**При отправке работы** это упрощение стоит упомянуть в сообщении сабмита (не только здесь в README) — чтобы работодатель заранее видел разрыв с UX видео, а не находил его при сравнении.

Страница: `/edit`. API: `GET/POST /api/campaigns/{id}/offers`, `DELETE /api/campaigns/{id}/offers/{offer_id}`.
