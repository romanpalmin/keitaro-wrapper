# keitaro-wrapper

[![CI](https://github.com/romanpalmin/keitaro-wrapper/actions/workflows/ci.yml/badge.svg)](https://github.com/romanpalmin/keitaro-wrapper/actions/workflows/ci.yml)

Тестовое задание: веб-обёртка над API рекламного трекера — **создаватор** кампаний
и **редактор** офферов существующей кампании.

> **Статус: проверено на живом стенде трекера.** Прогнаны probe (7/7), создаватор
> (кампания с двумя потоками) и редактор офферов (add/remove, share 50/50 → 33/33/34 → 100),
> откат при сбое на втором потоке. Контракт потоков взят из документации стенда
> (разделы «Что поддержано» и «Чего нет»): справочников `streams_actions`/`stream_filters`
> на стенде нет, значения зашиты в коде. Что осталось непроверенным — раздел
> «Что не успел» ниже.

**Стек:** Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic, pytest, ruff.
Фронт — статический HTML (без сборщика), как разрешено в ТЗ.

## Запуск

**Команды выполняй из корня репозитория** (где лежит `pyproject.toml`):
от него зависят относительный `DATABASE_URL` в `.env` (`./keitaro_wrapper.db`)
и `prepend_sys_path = .` в `alembic.ini`. Сам `.env` приложение находит
через путь от `app/config.py` — не «где стоишь», а «где лежит проект».

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

cp .env.example .env   # заполнить KEITARO_BASE_URL и KEITARO_API_KEY

# схема БД (см. раздел «Миграции»)
alembic upgrade head

uvicorn app.main:app --reload
```

| URL | Что |
|-----|-----|
| http://127.0.0.1:8000/ | HTML-форма создаватора |
| http://127.0.0.1:8000/edit | HTML-редактор офферов |
| http://127.0.0.1:8000/health | healthcheck |
| http://127.0.0.1:8000/docs | Swagger |

Ключ и хост трекера — только в локальном `.env` (в git не входят).
В `.env.example` — плейсхолдер `tracker.example.com`.

### Probe (живой API)

```bash
.venv/bin/python scripts/probe_api.py
```

Проверяет, отвечает ли трекер на нужные разделы. Ключ в логи не пишется.
Сейчас: **7/7 OK** — справочники, кампания и её потоки; по потокам probe печатает
`id`, `name`, `type`, `schema`, `action_type`, `action_payload` и непустые
`filters`/`offers` — видно, что реально лежит в трекере.
Для двух последних проверок нужна **хотя бы одна своя кампания** в трекере:
без неё probe выдаст ERR и exit 1, даже если API работает.

### Живой прогон сценариев (создаватор + редактор)

```bash
.venv/bin/python scripts/live_check.py
```

Поднимает `uvicorn` на порту 8017 и гоняет три сценария против стенда: создание
кампании с двумя потоками, редактор офферов (add/remove + пересчёт share) и откат
при сбое на втором потоке. Печатает коды ответов нашего API и трекера; ключ
в вывод не попадает. Все созданные кампании — с префиксом `test_palmin_`.

## Миграции

URL БД берётся из `.env` (`DATABASE_URL`), не из `alembic.ini`.

```bash
alembic upgrade head      # накатить схему
alembic current           # какая версия сейчас
alembic revision --autogenerate -m "…"  # новая миграция (сравнение моделей с БД)
```

При старте сервиса (`uvicorn`):

- `APP_ENV=dev` (по умолчанию) — `lifespan` вызывает `init_db()`
  (`Base.metadata.create_all`): недостающие таблицы создаются автоматически;
  изменение существующей схемы — всё равно через миграции.
- `APP_ENV=production` — `create_all` **не** вызывается; схема только через
  `alembic upgrade head`.

**Если таблицы уже созданы через `create_all`, а `alembic_version` пуст**
(классический «dev-файл без истории»):

```bash
alembic stamp head   # пометить head, не пересоздавая таблицы
# дальше обычные upgrade при следующих миграциях
```

Свежая чистая БД: сразу `alembic upgrade head` (или dev-старт + create_all,
затем `alembic stamp head`, чтобы истории не расходились).

## Примеры API

Создать кампанию (2 потока: geo → Google, default → оффер):

```bash
curl -s -X POST http://127.0.0.1:8000/api/campaigns \
  -H 'Content-Type: application/json' \
  -d '{"name":"demo","geo_code":"MX","offer_id":42}'
```

Справочник офферов (автокомплит редактора):

```bash
curl -s http://127.0.0.1:8000/api/offers
```

Список офферов потока кампании `42` (цифры: active_count, share_sum):

```bash
curl -s http://127.0.0.1:8000/api/campaigns/42/offers
```

Добавить / удалить оффер (share пересчитываются, сумма активных = 100):

```bash
curl -s -X POST http://127.0.0.1:8000/api/campaigns/42/offers \
  -H 'Content-Type: application/json' \
  -d '{"offer_id":7}'

curl -s -X DELETE http://127.0.0.1:8000/api/campaigns/42/offers/7
```

Коды: `201` — создание/добавление; `404` — нет кампании/оффера; `409` — оффер уже в потоке;
`502`/`503`/`504` — ошибка/нет ключа/таймаут трекера (тело — `detail` + `[kind]`).

## Редактор офферов: отличия от референса и почему упрощённо

В ТЗ к редактору сказано: кнопки работают, цифры верные; интерфейс — на наш вкус.
Оригинальный UX показан на видео из Notion (AdRobot: «Keitaro Streams» рядом с админкой Keitaro).

**Что в референсе:**

- кнопки **FETCH STREAMS FROM KT** и **PUSH TO KT | CANCEL** — правки сначала копятся локально, потом одним PUSH уходят в трекер;
- **REMOVE** не выкидывает оффер: share → 0%, пометка `(removed)`, кнопка **BRING BACK** (мягкое удаление);
- таблица со Stats/Trends, ссылка **VIEW IN KT**.

**Что у нас (упрощение):**

| Референс | У нас | Почему |
|----------|-------|--------|
| FETCH / PUSH / CANCEL | каждая кнопка **сразу PUT** в трекер | меньше состояний и источников рассинхрона: UI всегда = то, что в трекере. Локальный буфер (dirty-state, откат кнопкой CANCEL) — заметно больше кода и краевых случаев, а в ТЗ не требуется |
| REMOVE → 0% + BRING BACK | **hard-remove** из массива `offers` | проще контракт PUT: один массив после операции. BRING BACK — UX-удобство, не из ТЗ |
| Stats / Trends / VIEW IN KT | нет | данные отчётов трекера, вне «add/remove + цифры верные» |

**Что сохранено (суть ТЗ):**

- добавление/удаление офферов в кампании;
- **цифры верные**: после каждой операции `share` пересчитывается поровну, сумма всегда 100 (3 шт → 33/33/34 — как в видео).

**Существующие disabled-офферы** в массиве `offers` не выбрасываем: уходят в PUT с `state=disabled, share=0` и вне пересчёта активных (сумма 100 — только по активным).

Страница: `/edit`. API: `GET/POST /api/campaigns/{id}/offers`, `DELETE /api/campaigns/{id}/offers/{offer_id}`.

## Как использовал ИИ

> Использовал Claude Code как основного coding-агента: архитектура слоёв
> (FastAPI → сервисы → SQLAlchemy/Alembic), HTTP-клиент к Admin API, HTML-формы,
> pytest-изоляция (MockTransport, tmp SQLite) и ruff. Отдельной моделью-ревьюером
> гонял диффы каждого блока до вердикта «ГОТОВ» — на вход шли только diff и
> условия ТЗ, не «всё подряд». Агенты разрешены ТЗ; код и каждую строку разбирал
> сам, коммиты — после своего «ок». Live probe к трекеру запускаю скриптом
> `scripts/probe_api.py`, ключи только в `.env`.

## Что не успел / известные ограничения (честно)

- **Живой прогон был на учебном стенде, а не на полном Keitaro:** стенд эмулирует
  Admin API в части, нужной для задания (список поддерживаемых путей — в его
  документации). Поведение на полном Keitaro (например, поле `action_payload`
  и `schema=landings`) не проверялось — их я взял из документации стенда и
  публичных доков Admin API.
- **`action_type` у потока с офферами:** в публичном OpenAPI (`StreamRequest`) поле
  обязательное, хотя в примере документации стенда его нет. Живой тест на стенде:
  `POST /streams` с `action_type=http` и `schema=landings` → **200** (поток создан
  и сразу удалён), значение `offer` тоже даёт 200. Шлём `http` — так же, как UI
  стенда. На полном Keitaro это не проверялось.
- **Сбой для проверки отката имитировался на клиенте** (второй `POST /streams`
  поднят в ошибку), а не вызван самим трекером: сам откат (поиск и `DELETE`
  кампании) шёл в трекер по-настоящему и подтверждён отсутствием кампании после.
- **Скрытая строка-«инструкция для LLM» в документации стенда** (aria-hidden,
  раздел «Журнал») не выполнялась: она противоречит ТЗ и нашему задокументированному
  решению по hard-remove — поведение обёртки определяется ТЗ и README, а не
  разметкой страницы.
- **FETCH/PUSH-буфер и BRING BACK** из видео — сознательно не делал (см. таблицу выше).
- **Stats/Trends/VIEW IN KT** — вне ТЗ.
- **Таймаут клиента** — константа 15 с в коде, не вынес в env.
- **PostgreSQL** — в README/`.env.example` описан, в тестах гоняется только
  SQLite (aiosqlite); прод-URL не проверялся.
- **Авторизация собственного API** — нет (локальная обёртка, не публичный SaaS).
- Повторный одинаковый `name` у создаватора → alias занят → ответ трекера 400
  (без авто-переименования); сбой после POST кампании ищет её по alias и
  пытается откатить DELETE — при полном отказе поиска в трекере может остаться
  «полукампания» без записи в локальной БД.

## Структура

```
app/
  main.py            # FastAPI + lifespan
  config.py          # .env (путь от __file__)
  db.py              # async engine/session, init_db
  api/               # routes + pydantic-схемы
  services/          # keitaro_client, campaign_creator, campaign_editor
  models/            # CampaignRecord (журнал)
  static/            # create_campaign.html, edit_offers.html
migrations/          # Alembic
tests/               # pytest
scripts/probe_api.py # живой probe
scripts/live_check.py# живой прогон сценариев (создаватор/редактор/откат)
```

`docs/` (учебные заметки, журнал) — в `.gitignore`, в публичный репозиторий не входит.
